# 持续抓取与实时结果

## 已确认的原因

- 原界面默认抓取 300 条；爬虫在未指定数量时另有 500 条上限。
- 原数量上限计算筛选前的商品，筛选后可能只剩少量结果。
- 原滚动一次跳 6000 像素并跳到底部，可能漏过虚拟列表，且没有处理内层滚动容器。
- 连续四次无新增就结束，没有区分慢加载、验证、限速和真正结束。
- 原任务结束后才保存结果，运行时前端拿不到中间数据。

以上是代码确认的问题，不是所有反爬验证均已解决的证明。
用户明确授权现场测试后，旧可见浏览器方案在 4 分钟内读取了 140 条。
现场搜索接口返回 `rc-res-data` 包装数据，不能直接按普通商品 JSON 解析；
页面运行网站自身脚本后，仍可从已经渲染的卡片读取商品。
采用 Scrapling skill 的浏览器读取、会话一致性、退避和流式输出思路，
沿用项目现有 Playwright 运行环境，没有新增 Scrapling 依赖。

## 当前行为

- 上限留空时持续读取；填写上限时按本次符合筛选条件的去重商品计数。
- 连续分段滚动至当前列表底部，沿途读取卡片，接近底部减速；底部停止滚动并等新数据。
  分段等待约 140–260 毫秒，加载中暂停滚动；请求后至少等 8 秒再继续翻页，
  并根据响应耗时和限速次数提高间隔（最高 30 秒），429 另行遵守 Retry-After。
  兼容内层滚动容器，优先选择包含商品图片的容器，使用与当前 Chromium 版本一致的移动端 User-Agent 和 Client Hints。
- 抓取通过系统 Edge/Chrome 的 `--headless=new` 在后台运行，无商品浏览器窗口。
  原生浏览器执行网站 JS、网络请求和页面渲染，使用 Android 手机设备模式，视口 412 × 839，启用触屏；
  登录、验证与翻页复用本程序的持久配置目录，Cookie、站点存储持续保留。
  只有用户主动选择获取登录信息时才打开登录窗口。
- 每批结果去重合并到已有词条；原子替换文件，避免轮询读到半个文件。
- 界面约每秒轮询，仅传输变动商品；游标过期或服务重启自动回退全量。
- 只渲染当前页。新增数据不重置页码、筛选输入和滚动位置。
- 打开、关闭商品详情或切换标签时，按词条及列表条件保存纵向、横向位置。
- 顶部始终提供停止按钮；已保存数据在主动停止、访问拒绝或异常后保留。
- 429 有可取消的递增等待，遵守 Retry-After；等待后，若页面出现现场确认的
  “手机网络有问题，请检查网络”卡片，使用该卡片自己的刷新按钮续载。
  普通加载错误也先等待再重试，全程最多三次；401/403、系统繁忙会结束并提示。
- 验证先等待页面自身检测运行，识别到 Cloudflare 复选框时只尝试一次。
  网站滑块、点选等需要用户处理时，在软件内点击“前往验证”操作同一后台页面。
  画面只保存在内存，HTTP 线程排队传递用户输入，抓取线程执行点击、拖动及文字输入。
  接管时暂停自动翻页；关闭操作页不会跳过验证，“继续抓取”也不能覆盖验证检测结果。
  验证通过后自动续抓，等待 10 分钟仍未恢复则保留结果并结束。
- “前往验证”只在明确需要人工验证时显示；正常抓取、自动恢复和网络停顿均不显示。
  登录失效提示重新登录。无新增持续 60 秒且加载错误重试无效时，保留结果并结束。
  只有页面/接口明确结束才显示没有更多结果。

2026-10-29 调整滚动节奏和验证入口。滚动速度变化用于减少空等和漏读，
不能保证避开网站风控，也不将人工浏览一万条视为自动抓取可达到相同数量的证据。
- API 的 total 仅供诊断，不作为保证完整性的总量或隐含抓取上限。

## 本地诊断

每次任务结束写入 `data/searches/<词条>.run.json`：读取数、符合条件数、

不记录 Cookie、请求头或原始响应正文。重试同一词条会更新此文件。

## 2026-11-01 手机设备模式验证

用户提供的手机 Edge HAR 中，54 次翻页全部 HTTP 200，包含 1080 个不同商品 ID；手机与电脑使用同一 Wi-Fi。网页源码在生成 anti_content 前根据移动端 User-Agent 选择调用分支。

本轮在电脑原有登录会话中切换到 Chromium 标准手机设备模拟，网站仍自行生成每页参数。实时搜索 switch，50 次响应全部成功，保存 1000 个不同商品 ID，耗时 533.72 秒，0 次限速，到达测试上限后停止。未把 HAR 商品导入为实测数据，也未覆盖商品库。

配置位于 pdd/browser/mobile.py，由登录和抓取共用；同步视口、触屏、移动端 UA 与 Client Hints，浏览器版本来自本机引擎。离线浏览器用例验证了会话持久化、截图、点击及中文输入。没有关闭验证码或忽略服务器限速。此结果只证明该词条、该会话本次达到 1000 条，不代表无限抓取。

## 2026-11-01 软件入口复现与代码调整

用户实际使用及真实任务入口对照中，键盘和 switch 仍在 140 条后限速。已排除旧源码未重启，且记录确认移动端 UA、触屏和屏幕配置生效；仅更改视口或完整复用旧初始化顺序未恢复。这些失败说明前述单次 1000 条实验不能作为稳定修复结论。

本轮改动：自动翻页改为浏览器触屏滑动输入；连续 HTTP 429 或服务器要求较长冷却时保留浏览器和内存去重集合，冷却后由用户继续一次；如果再次限速则再次暂停，只有实际出现新商品才重置失败预算。命令行无继续按钮时仍结束并保留结果。停止或关闭软件会结束会话，不宣称跨重启恢复分页。

运行诊断增加 browser_mode=android-touch-v2、浏览器环境、pause_count 和 manual_resumes，不记录凭证。按用户要求，这批改动没有运行抓取或功能测试，效果由用户实际使用验证。

## 2026-11-01 手机限速抓包后的调整

离线比较两份用户 HAR：限速前 54 次搜索成功、1080 个不同商品；限速后 2 次 403/40001（网页定义为登录失效）、1 次成功、6 次 429/40002（接口繁忙），失败涉及多个词条的第一页且没有 Retry-After。手机样本的 anti_content 均变化且请求头与正文一致，尚不能判断服务端限制维度，也没有还原签名内部算法。

本轮改为首次 HTTP 429、40002 或页面繁忙/频繁提示即暂停保留页面，取消原来的连续自动限速重试。等待下限从 60 秒逐次倍增至 900 秒，更长的服务器等待要求优先；等待结束不代表网站恢复。用户继续后只有出现新商品才重置失败计数，无新商品则再暂停。40001 单独提示登录失效。诊断版本为 android-touch-v3，响应摘要包含错误码和数值页码，不包含登录凭证。

仅做 Python 语法解析，未运行抓取或功能测试；1000+ 条的稳定达成仍由用户实际使用验证。

## 累计目标与采集效率（待用户实际验证）

用户接受累计到 1000+，但要求耗时接近手动操作。桌面任务现将历史符合当前条件的商品计入目标，并分别记录 existing_matched、cumulative_matched、new_goods、saved_new_goods 和本次 elapsed_seconds。重复 ID 不增加新增数量，未达目标仍标记为部分完成；已有数据达标则不开浏览器。

正常翻页按请求起点计时，基础间隔 2.5 秒；等待在途请求结束及 0.4 秒渲染时间，按平滑响应耗时放慢。限速暂停不变，只有新商品到达才逐步恢复正常节奏。无变化的商品合并不再重写文件。当前诊断版本 android-touch-v4。

仅检查 Python/JavaScript 语法，没有运行功能或抓取测试。以上减少软件自身等待和重复工作，不代表解除 429，不承诺完成时间，也不宣称关闭软件后可恢复网站分页游标。

## 首屏 403 与重新登录缺陷

最近的软件“耳机”日志（android-touch-v3）记录第 1 页 HTTP 403，随后通用 Error，0 条商品；错误正文未能读取，不能直接断言此响应一定是 40001。旧的 1000 条成功记录只有响应摘要，没有完整请求抓包，无法据此确认具体哪项请求差异导致后续 140 条失败。

代码确认另一个直接缺陷：主动获取登录信息时，只要导入的旧 Cookie 含身份标记便立即返回，可能尚未完成重新登录就关闭窗口。现改为仅在用户主动获取登录时清除三个旧身份 Cookie，保留其余浏览器状态；等新身份 Cookie 出现且登录/验证页面结束后再保存。页面读取只对上下文被导航销毁的两类明确错误返回空快照，交主循环识别登录页，其他异常仍报告。新日志增加 error_stage，诊断版本 android-touch-v5。

仅静态语法检查，未启动登录、浏览器或抓取测试。没有导入旧 HAR 商品，没有证明 1000+ 稳定达成；AGENTS.md 保持未解决。
